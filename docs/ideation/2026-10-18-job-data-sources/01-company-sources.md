# 원천 경로: 기업에게서 직접 받기

조사일: 2026-10-18 · 워커 A · 기준: [문제 정의](00-problem.md) 4절

## 1. 결론과 조사 범위

**표본 20곳 중 키·승인 없이 매일 공고를 자동 수신할 수 있다고 확인한 기업은 0곳, 확인 비율은 0/20 = 0%다.** 실제 가능 기업이 0%라는 뜻이 아니다. 제한된 표본 열람에서 공식 무인증 공고 API·채용 전용 피드·구직자용 신규 공고 메일을 검증하지 못했다는 뜻이다. 나머지 20곳의 가능 여부는 미확정이며, 미확정을 불가로 세지 않았다.

기업 공식 채용 사이트는 사람이 원문을 확인하는 경로로 유용하다. 그러나 국내 ATS의 ‘Open API’는 구직자에게 모든 고객사의 공고를 개방하는 API가 아니라 **채용 기업이 자기 워크스페이스를 연동하는 인증 API**였다. 가장 유망한 후속 방향은 ① 기업이 구직자에게 제공하는 알림 메일을 사용자가 직접 구독한 뒤 자기 수신함에서 가져오기, ② 기업/ATS가 공고 전용 RSS·JSON 피드를 명시적으로 제공하도록 하는 경로다. 두 방향 모두 이번 표본에서 즉시 적용 가능한 공급처를 확보한 것은 아니다.

### 방법과 해석의 한계

- 국내 대형 IT 서비스·그룹 SI와 클라우드/MSP·IDC 사업자를 목적 표집했다. 선정 이유는 직무 수요의 구조적 관련성이다. **20곳 모두에서 신입 SE를 자주 채용한다는 빈도 통계를 확인한 것은 아니다.** 현재 채용 중임과도 구분한다.
- 회사당 공식 채용/소개 페이지 1~3개 수준을 열람하고, robots.txt 및 발견된 sitemap·피드만 별도 소량 점검했다. 잘못된 후보 주소·403·429·DNS 실패는 실패로 기록했으며, 차단을 우회하거나 API 엔드포인트를 탐색·반복 호출하지 않았다. 계정 생성·구독 신청·지원·문의 발송은 하지 않았다.
- 웹 검색/열람 도구는 캐시나 텍스트 변환 결과일 수 있다. 원문 HTML 점검 결과와 다르면 양쪽을 적었다. HTTP 성공이나 검색 노출은 자동 이용 허락을 뜻하지 않는다.
- ‘원문 미검출’은 **열람한 진입/목록 HTML에서 `JobPosting`을 찾지 못함**이다. 상세 페이지나 JavaScript 실행 후에도 JSON-LD가 없다는 단정이 아니다. HTML 원문을 얻지 못하면 ‘확인 못 함’이다.
- robots는 일반 `User-agent: *` 기준으로 조사했다. Allow/미차단은 이용허락이 아니며, robots 부재·오류도 허락으로 해석하지 않는다. 이 문서는 연구 결과이며 AGENTS.md의 채용 사이트 스크래핑 금지 원칙을 바꾸지 않는다.

## 5. 비율 산정과 완전성

분자는 다음 세 가지를 모두 확인한 기업으로 정의했다.

1. 기업/ATS가 공고 배포용으로 제공한다고 확인한 API·피드·신규 공고 알림이다.
2. 개인이 기업 API 키·사업자·제3자 심사 없이 이용 가능하다. 메일의 일회성 사용자 구독은 별도로 표시한다.
3. 매일 사람의 페이지 열람 없이 신규 공고를 받을 구체적 경로가 확인된다.

| 지표 | 결과 | 해석 |
| --- | --- | --- |
| 키·승인 없이 자동 수신 **확인** | **0/20 = 0%** | 발견·검증률의 하한이며 실제 제공률의 추정치가 아님 |
| 자동 수신 가능 여부 미확정 | 20/20 = 100% | 미발견, 본문 셸, 오류·차단, 상세 미점검 등이 포함 |
| ATS 인증 공고 API 존재가 확인된 시스템의 표본 기업 | 4/20 = 20% | 현대오토에버·GS ITM(그리팅), 메가존·베스핀(나인하이어). 기업별 API 활성화/이용권은 미확정 |
| 유효 robots에서 조사한 공개 채용 경로 미차단 | 8/20 = 40% | SK, 현대오토에버, CJ, NHN, kt ds, kt cloud, DB, 클루커스. **자동 수집 허용 비율이 아님** |
| 일반 에이전트 전체 차단 확인 | 1/20 = 5% | 포스코; 나머지 11곳은 규칙 확인 못 함 |

확인된 SK sitemap은 고정 메뉴 11개뿐이다. sitemap이 있다는 사실만으로 전체 공고 ID 집합을 만들 수 없다. RSS도 보통 최근 항목만 남기므로 ‘끝까지 받음’과 ‘기간 중 모든 신규 공고를 받음’이 다르다. 알림 메일은 발신 측 전체 발송 수를 모르면 미수신·필터 누락을 계산할 수 없다.

따라서 완전성의 분모는 ‘국내 모든 공고’가 아니라 **사용자가 승인한 기업 × 검증된 경로 × 명시한 기간**이어야 한다. 수신 성공 시각, 최종 정상 조회 시각, 오류·차단, 원문 URL, 누락 여부를 알 수 없는 기업을 따로 표시한다. 원천이 공고 총수를 주지 않으면 총수를 추측하지 않는다.

## 6. 방식별 아이디어와 7개 기준 평가

상·중·하는 모두 유리할수록 상이다. ‘구현·유지 비용 상’은 비용이 낮다는 뜻이다. 조건부 아이디어는 전제가 충족된 뒤를 평가하되, 현재 공급처가 미확보인 점은 접근성·범위 점수에 반영했다. 점수는 실측이 아닌 이번 회의의 판단이다.

| 방식 | 정당성 | 개인 접근성 | 범위 | 완전성 검증 | 자동화 | 구현·유지 비용 | 기존 구조 적합성 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A. 기업 신규 공고 메일 → 사용자 수신함 입력 | 상: 기업이 구독자에게 보낸 공고를 본인이 이용 | 중: API 기업 승인은 줄지만 구독 기능·메일 읽기 권한은 필요, 표본 미확보 | 하: 실제 구독 가능 기업 수 확인 못 함 | 하: 받은 메일 수는 알지만 발송 누락 분모 없음 | 상: 구독 이후 자동 수신 가능 | 중: 발신자별 형식 변화·중복·스팸함 처리 필요 | 중: 원문 보존은 가능, ‘메일 없음=수집 완료’로 바꿀 수는 없음 |

| F. 채용 화면의 내부 JSON 호출 재사용 | 하: 공개 화면의 내부 통신은 자동 수집 허락 증거가 아님 | 중: 일시적으로 무인증일 수 있으나 확인 못 함 | 중: 여러 플랫폼에 적용 가능하다는 기술적 가설 | 중: 내부 total도 공개 계약·일관성 보장 없음 | 중: 토큰·차단·개편으로 중단 가능 | 하: 비공식 API 변경에 취약 | 중: 형태만은 맞출 수 있으나 원천 계약 불명 |

- **A의 구체안:** 사용자가 기업의 ‘신규 공고 알림’에 직접 가입한 경우에만 자기 메일 원문을 전달한다. 제목만으로 확정 탈락시키지 않고 본문 부족은 확인 필요로 둔다. ‘인재풀 등록’, 마케팅 뉴스레터, 전형 상태 알림은 신규 공고 알림과 별도 소스로 취급한다. 이번에는 신청하지 않았다.
- **B의 구체안:** 기업이 ‘공개 공고 목록 전체’를 제공하는 피드를 찾으면 ID·제목·기간·직무·근무지·원문 URL을 보존한다. 최근 N개만 주면 보존 기간과 확인 주기를 기록하고 완전 수집으로 표시하지 않는다. 클루커스의 발견 RSS는 채용 전용임이 확인되기 전에는 이 후보에 넣지 않는다.
- **C의 구체안:** 기업이 수집을 허용한 경우에 한해 sitemap은 URL 발견, JSON-LD는 표준 필드 추출로 역할을 나눈다. 이것도 페이지 자동 읽기이므로 현재 프로젝트 금지 원칙 아래에서 바로 구현할 수 없고 별도 결정이 필요하다. robots Allow나 Google 검색 노출을 허가로 대체하지 않는다.
- **D의 구체안:** 기업 키를 구직자에게 공유해달라고 하지 않고, 기업이 공개 공고 필드만 제한한 별도 피드/프록시를 제공하는 형태가 낫다. 지원자·평가·비공개 공고 권한을 요청하지 않는다. 키 없는 조건에는 부합하지 않으므로 기본안에서 제외한다.
- **E의 구체안:** 제목·원문 URL·채용 상태·갱신시각·경력구분을 최소 항목으로, 전체 현재 공고 및 종료 공고 변동분을 기업이 내보낸다. 정규화되지 않은 항목을 생략하더라도 원문을 남기고 확인 필요로 처리한다. 개인 1명의 실행안보다는 ATS 사업자 제안/중장기 방향이다.
- **F는 기본안에서 제외:** KT 홈에 노출된 API 호스트나 그리팅의 화면용 데이터가 보이더라도 인증 우회·비공식 수집으로 확장하지 않는다. 기술적으로 호출 가능함과 정당하게 자동 수신 가능함은 다르다.

## 7. 가장 유망한 1~2개와 다음 검증

**1순위: A, 사용자에게 정식으로 발송되는 기업 채용 알림 메일.** 승인 장벽을 낮추면서 원천이 전달한 데이터라는 장점이 있다. 다만 이번 20곳에서는 신규 공고 구독 기능을 확증하지 못했다. 다음 검증은 관심 기업 3~5곳을 사용자가 정한 뒤 공식 FAQ/구독 안내를 확인하는 일이다. 실제 가입과 메일 접근 권한은 사용자가 결정해야 하며, ‘놓치지 않는다’가 아니라 ‘등록한 알림 경로에서 받은 공고를 기록한다’로 약속해야 한다.

**2순위: B, 이용조건이 명시된 공고 전용 피드.** 키 없는 자동화와 1인 유지비 측면에서 가장 깔끔하다. 공급처를 찾기 전 구현부터 시작하지 않는다. 전체 목록·총수·상태·갱신 주기·이용조건 중 무엇이 제공되는지 확인한 뒤, 부족하면 ‘부분 수집’으로 기록한다. 이번에 발견한 회사 일반 RSS와 고정 메뉴 sitemap은 채용 피드 확보로 세지 않는다.

현재 `backend/app/adapters/base.py`의 `SourceName`은 `saramin | work24`로 한정되어 있다. 새 경로는 타입·DB 소스 구분 등 주변 확장도 필요하다. 특히 메일은 페이지 조회 모델과 달라 별도 수신 단계 후 원문/정규화 파이프라인으로 연결하는 편이 자연스럽다. 어느 경로든 정보 부족을 탈락으로 바꾸지 않고, 기업 목록/키워드는 사용자 승인 후 고정하며, 지원은 원문 URL을 유지한다.

## 8. 검증 기록과 남은 문제

- 변경 파일: 이 문서 하나. 기능 코드·의존성·다른 문서·커밋은 변경하지 않았다.
- `make check`: 종료 코드 0. Ruff 통과, 포맷 53파일 통과, mypy 24파일 통과, 백엔드 189개 및 웹 1개 테스트 통과. 문서 전용 작업이므로 새 기능 테스트/의도적 실패 테스트는 해당하지 않는다.
- 조사 실패도 근거로 남겼다: 후보 `careers.megazone.com`은 열람 실패 후 공식 경로를 확인했고, `recruit.nhn.com`은 DNS 실패 후 `careers.nhn.com`을 확인했다. 다우 400, 채용 원문 403/429, robots 비텍스트/오류는 성공으로 바꾸지 않았다.
- 남은 문제: 실제 신입 직무별 채용 빈도, 상세 JSON-LD, 기업별 알림 구독, ATS 이용약관의 자동 수신 허용 범위는 추가 확인이 필요하다. 이번 조사는 표본 탐색으로, 정기 수집의 합법성이나 전체 채용시장 커버리지를 입증하지 않는다.
