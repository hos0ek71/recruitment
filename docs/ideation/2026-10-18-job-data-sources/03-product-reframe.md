# 제품 재정의: 이미 오는 공고와 내가 발견한 공고를 빠짐없이 관리하기

작성·공식 자료 확인: 2026-10-18 · 아이디어 회의 C

## 1. 제안과 판단 범위

가장 유망한 방향은 **구직자가 이미 수신하는 공고 메일을 개인 공고함으로 모으고, URL 직접 저장으로 빈틈을 기록하는 조합**이다. 제품의 약속을 “모든 포털의 모든 공고 수집”에서 “승인한 수신 채널의 도착분을 누락 없이 처리하고, 외부에서 발견한 누락을 측정”으로 바꾼다. 수신 경로가 확보돼도 전체 시장의 포괄률은 아직 모른다.

이 문서는 설계 변경 제안이며 구현·정책 변경 승인이 아니다. 기존의 코드 필터, 탈락 근거, 정보 부족 시 확인 필요 통과, 원본 분리, 승인 조건만 자동 실행, 원문 지원 링크를 유지한다. AI는 기존 허용 범위를 유지하며, 메일 추출은 우선 결정적 파서와 사용자 확인으로 설계한다.

표시 의미: **확인**은 공개 공식 자료 또는 저장소 코드로 확인한 사실, **제안/추정**은 설계 선택이나 검증 전 가설, **확인 못 함**은 근거를 확보하지 못한 항목이다. 외부 계정 로그인·가입·알림 신청, 실제 메일함 접근, 채용 API 호출, 페이지 자동 수집은 하지 않았다.

## 2. 공식 자료로 확인한 수신 경로

**입력 품질 가설:** 메일에 제목과 공고 URL만 있어도 발견함에 넣을 수 있다. 회사·지역·신입 여부가 없으면 추정해서 채우거나 탈락시키지 않는다. 추적 링크만 있는 경우 네트워크로 리디렉션을 따라가지 않고 원문 URL을 사용자에게 확인받는다. 메일 원문은 외부 이미지·추적 픽셀·스크립트를 실행하지 않고 처리한다. 실제 소스별 파서는 표본 확인 뒤 결정한다.

### 2.2 Gmail API: 개인 메일함에 대한 공식 접근

- **확인:** 본문 읽기의 최소 후보는 `https://www.googleapis.com/auth/gmail.readonly`이다. 읽기 전용이지만 restricted scope다. `gmail.metadata`는 헤더·라벨만 읽어 공고 본문 추출에 부족하고, 전체 삭제까지 허용하는 `https://mail.google.com/`는 필요하지 않다. [Gmail 공식 범위](https://developers.google.com/workspace/gmail/api/auth/scopes)
- **확인:** OAuth 2.0 사용자 동의로 authorization code를 교환하고, 예약 실행에는 offline access와 refresh token을 사용한다. API 키만으로 개인 메일함을 읽는 모델이 아니다. 현재 FastAPI 배포에 연결할 때는 웹 애플리케이션 OAuth 클라이언트와 등록한 redirect URI를 쓰는 것이 제안이다. 클라이언트 비밀값·토큰은 환경변수/비밀 저장소로만 관리하고 문서·로그·픽스처에 넣지 않는다. [공식 웹 서버 OAuth 흐름](https://developers.google.com/identity/protocols/oauth2/web-server)
- **확인:** External/Testing 상태에서 Gmail 범위를 쓰면 refresh token은 통상 7일 후 만료된다. 개인용 검증 예외는 있지만 미검증 경고와 사용자 수 제한이 남는다. **검증 면제와 장기 무인 실행은 별개**로 확인해야 한다. 서버에 restricted 데이터 저장·전송 시 일반적으로 보안 평가 요구가 있으므로, 개인용 예외의 실제 적용 범위와 배포 상태는 구현 전에 다시 확인한다. [토큰 만료 조건](https://developers.google.com/identity/protocols/oauth2/), [restricted scope 검증·개인용 예외](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)
- **확인:** `messages.list`는 `q`와 `labelIds`로 검색할 수 있고, 목록은 ID와 thread ID만 준다. 본문은 `messages.get`으로 추가 조회한다. 다음 페이지는 `nextPageToken`이며 `resultSizeEstimate`는 **추정값**이다. 이를 공고 총수로 사용하면 안 된다. 날짜 문자열은 PST 기준이므로 KST 기간은 epoch 초로 명시한다. [검색·날짜 기준](https://developers.google.com/workspace/gmail/api/guides/filtering), [목록 계약](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list)
- **제안:** 사용자가 기존 알림에 붙인 전용 라벨과 승인 발신자·기간만 조회한다. 라벨 제한은 앱의 실행 제한이지 OAuth 권한이 라벨 하나로 줄어드는 것은 아니다. 발신자 주소·라벨은 실제 메일로 확인하고 임의로 만들지 않는다. 전체 메일함 원문을 저장하지 않으며 공고 메일 원문도 개인정보를 포함할 수 있어 비공개 저장·보존 기간·삭제 기능을 정해야 한다.

### 2.3 Google 알리미

**확인:** 새로운 Google 검색결과에 대해 이메일을 받을 수 있고, 빈도·사이트 유형·언어·대상 지역·결과 수를 설정할 수 있다. 서비스가 이미 찾은 결과를 공식 이메일로 받는 경로다. 이 도움말에서 프로그래밍용 Google 알리미 API 또는 RSS 제공은 **확인 못 함**이므로 이메일만 기본안으로 삼는다. [Google 알림 만들기](https://support.google.com/websearch/answer/4815696?hl=ko)

**제안:** 사용자가 승인한 `"신입" "인프라" "채용"`, `"서버 운영" "채용"` 같은 주제 및 관심 기업 채용 도메인 조건으로 알림을 직접 만든다. 정확한 검색식 지원·결과 품질은 미리보기에서 검증한다. 시스템은 도착한 메일의 결과 링크만 받아 발견함에 넣으며 링크 대상 페이지를 자동 요청하지 않는다.

**한계:** 검색 색인 밖·로그인 필요·짧게 열렸다 닫힌 공고는 놓칠 수 있고, 새 검색결과가 새 공고라는 보장도 없다. Google도 재크롤링에 수일~수주가 걸릴 수 있고 색인을 보장하지 않는다고 명시한다. 따라서 “웹 전체 감시”가 아니라 “검색에 발견된 결과의 보조 채널”이다. 제목·요약만으로 근무 조건이나 마감을 확정하지 않는다. [Google 색인·재크롤링 한계](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl)

## 3. 아이디어와 사용자 흐름

각 흐름은 제안이며 이번 작업에서 실행하지 않았다. C1을 주 경로, C4를 모든 경로의 보완 입력으로 우선 검증한다.

### C1. 내 공고 메일함: 포털 알림을 Gmail로 통합

1. 사용자가 이미 받는 사람인 등 알림에서 대상 발신자와 라벨을 선택한다.
2. 읽기 전용 OAuth 동의 후 승인한 기간·라벨의 메일만 가져온다.
3. 각 메일의 공고 카드를 추출해 중복을 합치고, 부족한 조건은 확인 필요로 남긴다.
4. 매일 “메일 12통 중 처리 12통, 카드 40건 중 해석 37건, 확인 필요 3건”과 원문 링크를 확인한다.

### C2. 관심 기업의 직접 채용 소식함

1. 사용자가 이미 구독한 기업 공식 채용 메일을 선택한다.
2. 기업별 발신자와 소식 종류를 승인한 뒤 같은 Gmail 입력기에 연결한다.
3. 일반 홍보와 개별 채용 링크를 분리하고, 구분 실패는 확인 대기열에 둔다.
4. “관심 기업 10곳 중 수신 경로 확인 4곳”을 보고 경로가 없는 기업도 표시한다.

### C3. Google 알리미를 통한 새 페이지 발견함

1. 사용자가 승인한 직무 키워드·기업 조건으로 알리미를 직접 설정한다.
2. 도착 메일을 Gmail 입력기로 읽어 제목·결과 링크를 후보로 저장한다.
3. 사용자가 원문을 열어 실제 공고인지 확인하고 필요한 정보를 직접 보완한다.
4. 기존 소스에 없던 공고 수와 발견 지연을 확인해 노이즈가 큰 알림을 수정한다.

### C4. URL 붙여넣기: 가장 작은 개인 공고함

1. 사용자가 직접 발견한 공고의 URL을 복사한다.
2. 앱에 URL과 선택적 제목·회사·본인이 확인한 조건을 입력한다.
3. 서버는 페이지를 가져오지 않고 입력 원본을 저장하며 중복 후보를 보여준다.
4. 저장 전에 이미 시스템에 있었는지를 기록해 외부 발견 표본의 누락률을 측정한다.

### C5. 북마클릿: 현재 페이지 URL·제목만 저장

1. 사용자가 공고를 직접 읽고 북마클릿을 누른다.
2. 현재 URL과 문서 제목만 앱의 확인 폼으로 보낸다.
3. 사용자가 확인·수정한 뒤 저장하고 부족한 조건을 직접 보완한다.
4. 본문 DOM 추출·목록 순회·다음 페이지 이동은 포함하지 않는다. 사이트 CSP 등 실제 동작 제약은 검증이 필요하다.

### C6. 브라우저 확장: 사용자 선택 부분만 가져오기

1. 사용자가 현재 공고에서 필요한 조건 문장을 선택하고 확장 버튼을 누른다.
2. 임시 `activeTab` 권한으로 현재 페이지 URL·제목과 사용자가 선택한 텍스트만 확인 폼에 옮긴다.
3. 사용자가 저장할 내용과 출처를 확인한다. 쿠키·로그인 토큰·숨겨진 API·전체 본문은 수집하지 않는다.
4. 권한 회수·미지원 페이지는 URL 입력으로 돌아간다. 배경 탐색이나 예약 실행은 하지 않는다.

Chrome 공식 문서는 사용자 호출 시 현재 탭에 임시 접근을 주는 `activeTab`을 설명한다. 이 기술적 권한은 채용 사이트의 이용 허락을 뜻하지 않는다. [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)

### C7. 모바일 공유: 읽던 공고를 공유 메뉴로 저장

1. 사용자가 모바일 브라우저에서 읽는 공고의 공유 메뉴를 누른다.
2. 지원 기기에서는 설치한 웹앱/앱을 공유 대상으로 선택해 URL·제목을 전달한다.
3. 확인 화면에서 저장하고, 공유 텍스트만 전달된 경우 URL을 직접 보완한다.
4. 미지원 기기에서는 C4로 전환한다. 공유 대상 등록 방식과 브라우저·OS별 지원은 이번 조사에서 **확인 못 함**이다.

## 4. 일곱 기준 평가

`상`이 유리하다. 따라서 구현·유지 비용의 상은 **비용이 낮다**는 뜻이다. 범위는 SE·인프라 신입 채용시장 대비 잠정 평가로, 실제 비율은 모두 미측정이다. 수치처럼 보이는 근거 없는 포괄률을 부여하지 않았다. 각 칸은 점수와 근거 한 줄이다.

| --- | --- | --- | --- | --- | --- | --- | --- |

**위험의 구분:** C4·C5·C7의 URL 저장은 서버가 대상 페이지를 요청하거나 포털 DB를 복제하지 않는 설계다. C6에서 본문 일부를 옮기는 행위는 별도 이용조건 확인이 필요하며, “내가 보고 눌렀다”는 사정만으로 허용이 확정되지 않는다. 반복 저장으로 실질적 DB를 구축하거나 전체 본문·이미지를 축적하면 규모와 사용 방식에 따라 위험이 달라질 수 있다. 로그인 세션 재사용, 백그라운드 전체 탐색, 자동 다음 페이지, 서버의 URL 상세 자동 요청은 이 제안에 포함하지 않는다. 특정 포털 약관이 이러한 개인 저장을 명시적으로 허용하는지는 **확인 못 함**이다. C6를 구현하려면 기존 스크래핑 제외 원칙과의 경계도 별도 결정해야 한다.

## 5. ‘빠짐없이’의 재정의와 측정

**제품 문구 제안:** “등록한 채널의 받은 공고를 모두 처리합니다. 전체 시장을 얼마나 놓치는지는 외부 발견 표본으로 확인합니다.” ‘확인 불가’와 실패를 완료율에서 숨기지 않는다.

| 층위·지표 | 분자 / 분모 또는 정의 | 기록·주의점 |
| --- | --- | --- |
| API 소스 완전성 | 쿼리에서 받은 고유 공고 수 / API가 알려준 정확한 총수 | 같은 조건·기간·단위로 비교. 총수 미제공이면 비율은 N/A. 중복 병합 전 소스 ID 기준이다. |

메일함 변동으로 순회 중 빠지는 것을 줄이려면 고정 상한 시각, 기간 겹침 재조회, message ID 중복 제거를 제안한다. 모든 메일 열거·본문 읽기·저장이 끝난 경우에만 해당 기간 체크포인트를 전진시키고 실패는 다음 회차에 재처리한다. 신규 라벨 적용·발신자 변경으로 이전 검색에서 누락될 수 있으므로 초기에는 사용자가 날짜별 메일 목록과 주 1회 대조한다.

외부 표본은 주 1회 20분처럼 시간을 고정하고, 알림과 독립된 수동 기업 페이지 확인·별도 검색에서 연속으로 발견한 공고를 기록하는 방식을 제안한다. 미리 정한 키워드·날짜·조사 채널과 샘플 수를 함께 남긴다. 같은 포털 추천만 대조하면 공유 편향이 커진다. 표본 사전 보유율은 **전국 채용시장 재현율의 추정치라고 단정할 수 없고**, 표본이 적거나 0건이면 숫자와 함께 한계를 표시한다. 서로 의존적인 소스의 합집합·중복률만으로 시장 전체 크기를 추정하지 않는다.

화면 예시: `메일 12/12 처리 · 카드 37/40 추출 · 미해석 3건 · 시장 포괄률 알 수 없음 · 외부 표본 사전 보유 12/20(최근 2주)`.

## 6. 현재 계약·엔진에 끼우는 방법

### 6.1 코드에서 확인한 제약

- `backend/app/adapters/base.py`: `SourceName`은 `saramin | work24`만 허용한다. `SourceQuery`는 소스×키워드×지역과 `since`, `extra`를 갖고 `fetch_page(query, page: int, page_size)`는 정수 페이지를 받는다. `SourcePage`에는 공고 `items`, `total`, `raw_text`가 있지만 다음 페이지 토큰·완료 근거 필드는 없다.
- `backend/app/services/collection.py`: `SOURCES`와 소스별 예산·지역 변환이 두 소스 기준이다. `page += 1`로 순회하며 빈 `items` 또는 `len(received) >= total`에서 완료한다. 성공한 쿼리에만 워터마크를 갱신한다. API 호출은 `fetch_page` 1회 단위로 집계한다.
- `backend/app/domain/raw.py`: `RawItem`은 `source_posting_id`와 사전형 `payload`다. 초기 마이그레이션에는 raw·query·watermark·usage·posting_source의 소스 CHECK 제약이 있다. 따라서 **클래스 하나를 새로 구현하는 것만으로 어떤 제안도 그대로 연결되지는 않는다**.

### 6.3 계약 변경의 최소 방향과 함정

**권장 제안:** API 전체 페이지 수집은 기존 계약을 유지하고, 메일 수신·사용자 입력은 별도 입력 계층을 두되 원본 저장 이후 정규화·중복·필터·평가를 공통 서비스로 모은다. 메일을 먼저 받은 뒤 승인 조건 버전으로 평가하며, 한 메일을 여러 키워드 쿼리로 중복 읽지 않는다. 미승인 키워드나 새 발신자를 AI가 자동 추가하지 않는다.

메일도 공통 페이지 계약으로 통합하기로 결정한다면 `cursor/next_cursor`, `has_more`, `completion_basis`, `total_kind(exact/estimate/unknown)`와 메시지·공고 각각의 처리 수가 필요하다. 실제 이름과 스키마는 추후 설계 대상이다. 정수 페이지에 토큰을 어댑터 내부 상태로 숨기면 재시작·재시도가 불안정해지므로 피한다.

특히 **공고가 하나도 없는 메일 페이지에도 다음 토큰은 있을 수 있다**. 현재 엔진에 빈 `items`를 반환하면 뒤 메일을 받기 전에 완료되고, 연속 두 페이지에 신규 공고가 없으면 partial이 될 수도 있다. 메시지 순회 진행과 공고 신규성은 분리해야 한다. 또한 `messages.list` 1회+`messages.get` N회이므로 현재 `fetch_page`당 호출 1회 집계로는 실제 Gmail 사용량을 표현할 수 없다.

원본은 `gmail_message_id + 카드 위치/안정 식별자`로 발생 출처를 추적하고, 공고 중복은 확인된 원문 URL·포털 공고 ID와 기존 병합 규칙으로 별도 처리한다. MIME 원문과 추출 공고를 분리해 원본 불변식을 보존한다. URL만 입력한 경우 원본은 사용자의 URL·텍스트·입력 시각이지, 가져오지 않은 페이지 본문이 아니다. 서명된 URL이나 기능성 쿼리를 무조건 삭제하면 링크를 망가뜨릴 수 있어 원본 URL은 보존하고 비교용 키만 분리한다.

이 변경은 게이트·기능 완료 상태를 바꾸지 않는다. UI·수신 커넥터·스키마는 이번 작업에서 구현하지 않았다.

## 7. 가장 빨리 검증할 실험 두 개

### 실험 1 — 기존 수신 메일 20통의 공고화 가능성 감사

- **목적:** 가장 유망한 C1이 실제 사용자 데이터에서 성립하는지 OAuth·제품 개발 전에 확인한다.
- **소요:** 사용자 표본 선택 20~30분 + 사람이 카드·필드 대조 60~90분, 총 2시간 이내. 기존 메일이 없으면 결과는 ‘표본 확보 불가’이며 서비스 존재나 품질의 성공으로 간주하지 않는다.
- **방법:** 사용자가 이미 받은 최근 14일 채용 관련 메일에서 연속 20통까지 선택한다. 가능한 소스를 구분하되 잡코리아·원티드 표본을 임의 생성하거나 가입하지 않는다. 본인이 로컬에서 메일별 카드 수와 제목·회사·원문 URL·지역·경력·마감 포함 여부를 기록한다. 개인정보·토큰이 있는 원문은 저장소에 두지 않는다. 링크 대상은 자동 요청하지 않는다.
- **성공 기준(제안):** 10통 이상·공고 카드 30건 이상에서 90% 이상이 제목+직접 원문 URL을 갖고, 70% 이상이 회사명까지 제공한다. 회사·지역·경력·마감의 결측률을 각각 보고하고, 잘못된/추적 전용 URL과 비공고 메일을 따로 센다. 사람인 1소스만 충족하면 그 소스 한정 성공으로 보고한다.
- **다음 결정:** 성공하면 가장 일정한 한 소스의 읽기 전용 수신기를 TDD로 검증할 작업 명세를 만든다. 제목·링크조차 부족하면 전체 Gmail 통합보다 C4를 먼저 제품화한다. OAuth 무인 실행 가능성은 별도 사전 점검이며 이 실험 성공으로 인증 문제까지 해결됐다고 보고하지 않는다.

### 실험 2 — 수신함과 외부 발견 기록의 7일 대조

- **목적:** C1+C4 조합이 ‘몰랐던 누락’을 드러내는지, C3가 보조 가치를 가질 수 있는지 확인한다.
- **소요:** 준비 30분, 7일간 하루 10~15분, 마지막 대조 30분으로 총 약 2~3시간의 사람 작업. 실제 알림 설정·메일 접근은 사용자가 후속으로 승인하고 직접 수행할 실험이며 이번에는 실행하지 않았다.
- **방법:** 승인된 직무 조건으로 기존 수신 메일의 공고를 비공개 로컬 목록에 매일 기록한다. 별도 수동 검색·기업 페이지에서 연속 발견한 공고는 기록 **직전** 목록 보유 여부와 발견 시각을 체크하고 URL을 추가한다. 알리미는 이미 수신 중인 경우만 이번 비교에 포함하며, 미설정이면 C3 효과는 미측정으로 둔다.
- **성공 기준(제안):** 적합 여부를 사람이 확인한 외부 공고 10건 이상, 사전 보유 여부·발견 경로·시각 기록 100%, 수동 추가 누락 0건, 하루 기록 시간 중앙값 10분 이내. 메일 유래 적합 공고가 독립 표본의 절반 이상 이미 존재하면 주 경로 후보를 유지한다. 보유율이 낮아도 숨기지 않고 누락 경로를 분류한다.
- **관찰 기준:** C3 수신분이 있다면 다른 경로에 없던 적합 공고 2건 이상과 검토 10건당 적합 2건 이상을 보조 채택 기준으로 둔다. 외부 표본 10건 미만이면 성공 판정을 보류한다. 7일·소표본 결과를 시장 전체 포괄률로 일반화하지 않는다.

## 8. 검증과 남은 결정

- 변경 범위는 이 문서 하나이며 코드·의존성·게이트·다른 문서는 수정하지 않는다. 기능 구현이 없어 실패→통과 테스트 증거는 해당하지 않는다.
- 공개 자료 열람과 계약·엔진 대조를 수행했다. 실제 메일 양식, 잡코리아 현행 알림 제공, 기업별 직접 메일, 모바일 공유 호환성, 포털별 저장 허락, 개인 OAuth 장기 운영 조건은 미확인이다.
- 검증: `make check` 종료 코드 0. 백엔드 ruff·포맷·mypy 통과 및 pytest `189 passed`, 웹 ESLint·TypeScript 통과 및 Vitest `1 passed`를 확인했다. `git diff --check`도 종료 코드 0이었다. 검사 실패는 없었으며, 문서의 실험 두 개는 아직 실행하지 않았다.
- 다음 행동은 실험 1의 기존 메일 표본 감사다. 제품 구현 전에 수신 원본 보존 범위·개인정보 처리·새 입력 스키마와 기존 게이트 처리 방식을 결정해야 한다.
