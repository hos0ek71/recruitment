# 레드팀: 확보한 경로와 희망하는 경로를 구분하기

작성·검토: 2026-10-18 · 아이디어 회의 D

## 1. 판단

**1순위는 C1 기존 공고 메일 + C4 URL 직접 기록의 소규모 실험이다.** 메일 통합 구현이 아니라, 기존 메일 최대 20통을 사람이 감사하고 독립적으로 발견한 공고와 7일 대조하는 것이 먼저다. 실제 수신 표본조차 없으면 메일 주력안은 보류한다. 이 순위는 사용자의 민간·공공 선호가 미정인 상태에서 가장 적은 선행 투자로 핵심 가정을 깨 볼 수 있다는 판단이지, 범위가 가장 넓다는 확인이 아니다.

발산 문서는 조심스럽게 한계를 적었지만 평가표에는 아직 **공급처 확보 전의 이상적 운영 상태**가 섞여 있다. 기업 피드는 0/20곳 확보, 메일의 카드·필드는 미검증, 공공 API는 발급·실응답 미검증이다. 현재 세 문서 어느 것도 국내 신입 SE·인프라 공고 포함률을 입증하지 못한다. 반대로 미확인을 불가·시장 포함률 0%로 바꾸는 것도 잘못이다.

검토 범위는 [문제 정의](00-problem.md), [기업 경로](01-company-sources.md), [공공 경로](02-public-channels.md), [제품 재정의](03-product-reframe.md), [API 사실 검증](../../research/03-mvp-external-fact-check.md), [참고 MCP 검토](../../research/04-job-platform-mcp-review.md)다. 아래 A~F, I1~I12, C1~C7은 각 발산 문서의 식별자이며 **25개를 모두 검토**했다. A와 C2처럼 같은 공급 가정을 공유하는 아이디어는 독립된 범위 증가로 합산하지 않는다.

## 2. 근거의 강도와 최소 재열람

- **직접 재확인:** 이번 검토에서 공식 URL을 열어 해당 내용을 확인했다.
- **문서 근거 있음:** 발산 문서에 구체적 공식 URL과 확인 내용이 있다. 이번 검토에서 모두 다시 열지는 않았으므로 독립 재검증과 구별한다.
- **부분 근거:** 기능·명세는 있지만 치명적 가정의 핵심인 공급, 발급, 관련 공고 수 또는 실제 품질은 입증되지 않았다.
- **없음:** 제안 자체 또는 실험으로 확인할 가정이다. 실험 설계가 있다는 것을 검증 완료로 세지 않는다.

외부 재열람은 다음 **2개 URL 시도**에 한정했다. 키 신청·로그인·메일 접근·실제 채용 API 호출·채용 화면 수집은 하지 않았다.

나머지 출처는 아래에서 해당 문서의 절과 공식 URL을 연결해 추적한다. 정당성 평가는 법률 결론이 아니라 **확보된 이용조건과 미확인 범위**의 평가다. RSS 구독·공식 API·본인 메일 접근이라는 경로의 정당성이 첨부 원문 복제, 영구 저장, 다른 서비스 재배포 허락까지 포함하지 않는다.

## 5. 조합을 비교하는 공통 분모

1. **공급 확보:** 검증된 수신 경로 수 / 사용자가 승인한 경로 수. 미발급·미수신·미확인 경로를 분모에서 숨기지 않는다.
2. **전달 집합 완주:** API는 고정 조건·기간의 총수와 병합 전 고유 소스 ID 수, 마지막 페이지 도달·실패 여부를 함께 기록한다. 실행 중 총수가 바뀌면 불일치를 표시하고 고정 기간 재대조한다. 총수 일치만으로 원천 누락·실행 사이 마감 공고까지 보증하지 않는다.
3. **메일 처리:** 열거한 고유 message ID 전부의 처리 상태와, 사람이 센 카드 대비 올바르게 옮긴 카드 비율을 분리한다. 해석 실패도 기록 완료에 포함될 수 있으므로 처리율 100%를 추출 성공률로 쓰지 않는다. Gmail 추정 총수는 분모가 아니다.
4. **실용 범위:** 먼저 고정한 수동 조사 경로·키워드·기간에서 연속 발견한 적합 공고의 **입력 전 사전 보유 수 / 적합 공고 수**를 쓴다. 적합 미확인과 마감 미확인은 별도 건수다. 작은 편의표본이므로 시장 전체 포함률로 외삽하지 않는다.
5. **추가 가치·비용:** 각 채널이 최초 발견한 신규 적합 공고 수, 잘못 합친 공고 수, 검토 총분/적합 공고 수, 하루 작업시간을 함께 잰다. 제목이 같다는 이유로 모집별 경력·지역이 다른 공고를 합치지 않는다.

승인한 조건만 실험에 사용한다. 확정 필터는 코드, 불명 정보는 확인 필요, 원본과 정규화는 분리한다. 실험의 수동 적합 판정은 제품 코드 필터를 AI로 대체한다는 뜻이 아니다. 실패·부분 수집·원문 없는 후보를 완료 공고 통계에 섞지 않는다.

## 6. 조합 후보 3개와 1주 실험

아래 비용·수량은 **실험 설계용 추정과 제안 기준**이며 운영 실측이 아니다. 모든 후보의 실험은 미실행이다. 성공은 다음 단계 검토 자격이지 전체 구현·게이트 변경 승인이나 시장 완전성 입증이 아니다. 표본 부족은 성공도 실패도 아닌 **판정 보류**이며, 1주 안에 확보하지 못하면 해당 후보 구현 착수를 중단한다.

### 후보 1 — 기존 메일 주력 + URL 수동 그물 + 알리미 선택 보조 (1순위)

- **조합:** C1 주력, C4 외부 누락 기록. C2는 실제 받은 기업 메일이 있을 때만 같은 경로로 추가. C3는 기존 수신분이 있거나 사용자가 직접 설정한 뒤 보조로 검증한다. C5~C7은 이 단계에서 만들지 않는다.
- **예상 범위:** 사용자가 이미 받는 포털의 추천·저장 검색 도착분과 본인이 찾아낸 공고. 관련 메일이 없으면 주력 범위도 없다. 수시채용·알림 미발송·중소기업 공백이 남으며 전국 포함률은 미상이다.
- **완전성 측정:** 공통 분모 3·4를 사용한다. 수신된 카드의 처리와 외부 표본 사전 보유를 각각 보고한다. 추가 저장 뒤 보유 여부를 재면 100%로 오염되므로 반드시 입력 전에 대조한다.
- **1인 유지 비용:** 정상 주에도 검토·조건 보완 약 1~2시간/주, 양식·OAuth 장애가 난 주에는 추가 2~4시간을 가정한다. 초기 제품 구현은 별도 수신 계층·원본 정책·재처리가 필요해 작지 않다. 수신함 원문은 저장소에 넣지 않는다.
- **남는 위험:** 추천 편향, 원문 URL 없는 추적 링크, 메일 필드 부족, Gmail Testing 토큰 만료, 스팸·라벨 변경. 원천과 독립된 수동 표본도 작은 편의표본이라는 한계가 남는다.

**가장 싼 1주 실험:** OAuth·파서·UI를 만들지 않는다. 사용자가 최근 14일 메일에서 연속 최대 20통을 본인 기기에서 골라 카드 수·직접 원문 URL·회사·조건 결측을 센다. 이어 7일간 하루 최대 10분씩, 사전 고정한 별도 기업 페이지/수동 검색에서 연속 발견 공고를 비공개 로컬 목록으로 대조한다. 자동 링크 요청·본문 공유 없이 수행하며 사람 시간 총 3시간을 상한으로 둔다.

- **성공:** 메일 10통 이상·실제 카드 30개 이상, 제목+직접 원문 URL 확보 ≥90%, 회사명 확보 ≥70%. 별도 적합 공고 ≥10건에서 메일 유래 사전 보유율 ≥50%, 입력 전 대조 기록률 100%, 기록한 URL 유실 0건, 하루 기록시간 중앙값 ≤10분을 모두 충족한다. 메일 한 소스만 있으면 해당 소스 한정 성공이다.
- **중단:** 직접 원문 URL 확보 <70% 또는 외부 표본 10건 이상에서 사전 보유율 <30% 또는 하루 중앙값 >15분이면 메일 주력 구현을 중단한다. 70~90% URL·30~50% 보유·10~15분 구간은 보류하고 부족한 원인을 분류한다. 수신 표본이 10통/30카드 미만이면 공급 미확보로 보류하며 임의 데이터를 만들지 않는다.
- **보조 채택:** C3를 관찰했다면 다른 경로에 없던 적합 공고 ≥2건, 검토 결과 적합 비율 ≥20%, 추가 검토 ≤30분/주일 때만 유지한다. C3 미수신은 효과 0으로 확정하지 않고 미측정으로 남긴다.

### 후보 2 — 공공기관 API 주력 + 대학 RSS 그물 + URL 보조 (공공 취업 의향 조건부)

- **조합:** I1 P1 하나를 먼저 검증, I9 피드 2개를 보조 관찰, C4로 원천 외부 누락 기록. I3·I2는 첫 소스에 없는 지원 가능 공고가 확인된 뒤 추가하며 I10은 P1과 같은 원천의 수신 건강도 보조로만 취급한다.
- **예상 범위:** 공공기관 공시와 두 학교 게시판의 현재 창. 민간 SE 시장의 대체재가 아니다. 공무원 시험·지역 자격·학교 추천 대상이 맞지 않으면 데이터가 많아도 사용 가치가 낮다.
- **완전성 측정:** P1 쿼리 총수·고유 ID·끝 페이지, 표본 원문 대조. RSS는 응답 항목 완주와 이전 관찰 ID 보존을 기록하되 창 밖 원천 완전성은 미상. P1과 무관한 기업·대학에서 찾은 공고로 사전 보유율을 따로 센다.
- **1인 유지 비용:** 정상 주 약 1~2시간(자격·첨부 검토 포함), 코드표·API·피드 문제 주에는 추가 2~4시간 가정. 키·운영 심의·새 SourceName/DB 소스 확장을 포함하면 기존 어댑터 파일만 추가하는 작업이 아니다.
- **남는 위험:** 공공 취업 비선호, 적합 직무 희소, NCS 분류와 실제 운영업무 불일치, 동일 공고 여러 기관/게시판 중복, 첨부에만 있는 조건, 공고 갱신 중 총수 변동.

**가장 싼 1주 실험:** 먼저 사용자에게 공공기관 지원 의향을 확인한다. 동의 시 개발계정 신청과 제한된 실호출을 별도 후속 지시로 받아 P1만 검증한다. 새 제품 코드 없이 수동 감사표로 명세 코드표를 확인하고, 승인한 최근 30일 조건의 목록을 끝까지 읽은 다음 공고 최대 30건을 사람이 대조한다. RSS는 하루 1회씩 7회 관찰하고 신규 고유 적합 공고만 센다. 키 미발급 시 공개 화면 수동 검토는 관련성만 평가할 수 있으며 API 성공으로 보고하지 않는다.

- **성공:** 7일 내 키 사용 가능, 승인 범위의 목록 고유 ID 수=안정된 totalCount 및 끝 페이지 도달, 표본 최대 30건 중 유효 원문 링크 ≥95%, 사용자 지원 가능 적합 공고 ≥3건, 표본 1건당 검토시간 중앙값 ≤5분. 링크율 판단 표본은 ≥20건 확보해야 한다.
- **중단:** 7일 내 발급 불가이면 구현 착수 보류. 감사 30건에서 적합 0건 또는 중앙값 >10분이면 주력 채택 중단. 총수 불일치가 고정 기간 재조회 1회 후에도 남으면 완전 수집 판정·스케줄 구현을 중단하고 계약 확인으로 돌아간다. 표본 20건 미만은 링크 품질 판정 보류다.
- **그물 채택:** 대학 RSS가 7일간 P1에 없는 지원 가능 공고 ≥2건을 제공하고 총 검토시간 ≤30분이면 유지한다. 신규 공고 0건만으로 연중 가치가 없다고 단정하지 않으며, 추가 구현은 보류한다.

### 후보 3 — 개인용 공채속보 주력 + 메일 그물 + URL 보조 (키 발급 조건부)

- **조합:** I5 W1을 주력 후보로, 검증된 C1 메일을 상시채용 보조로, C4를 누락 기록으로 둔다. I8 사람인은 실제 승인되면 별도 비교 실험 후 교체·추가할 옵션이며 이미 확보된 공급으로 세지 않는다. I6·I7은 공고 주력에 넣지 않는다.
- **예상 범위:** 공채속보에 실린 대기업·중견 등 신입 모집과 기존 메일 도착분. 중소 운영업체·상시/소규모 채용 공백은 남는다. 기업 하나의 공채에 여러 모집이 섞이므로 공고 총수와 적합 모집 수를 분리한다.
- **완전성 측정:** W1의 목록 total·고유 공고 ID·마지막 페이지를 대조하고, 선택한 표본의 모든 모집 상세를 사람이 확인한다. 독립된 관심 기업 원문 수동 표본의 사전 보유율과 메일의 순증 공고 수를 각각 기록한다.
- **1인 유지 비용:** 정상 주 약 1~3시간, 상세 스키마·인증 문제 주에는 추가 2~4시간 가정. 목록 외 상세 호출 예산, 혼합 모집 분리·중복 병합과 메일 유지비가 겹친다.
- **남는 위험:** 공개 신청 안내와 개인 3종 접근의 불일치, 일일 한도·갱신주기 미확인, 대기업 공채 편중, 짧게 열렸다 닫힌 공고, 두 경로가 같은 인기 공고만 반복 제공하는 편향.

**가장 싼 1주 실험:** 사용자가 개인 공채속보 신청 자격·이용조건·키를 확인하고, 제한된 목록/상세 실호출을 별도 후속 지시한 경우에만 수행한다. 승인 조건으로 최근 30일 목록을 완주하고 공고 최대 20개 상세의 모집을 감사한다. 별도 관심 기업/검색에서 연속 발견한 적합 공고와 기존 메일 표본을 대조한다. 엔진 통합·로그인 우회·신규 포털 화면 자동 수집은 하지 않는다.

- **성공:** 7일 내 사용 가능한 개인 키와 이용범위 확인, 목록 total 대조·끝 페이지 도달, 감사 상세 중 필요한 모든 모집을 확인한 비율 100%, 지원 가능 고유 모집 ≥3개, 독립 적합 공고 표본 ≥10건에서 W1 사전 보유율 ≥50%, 메일 보조의 순증 적합 공고 ≥2건, 감사시간 총 ≤3시간을 충족한다.
- **중단:** 개인 발급 거절이면 후보 중단. 7일 내 발급 미완료는 보류하며 우회 수집하지 않는다. 상세 20개에서 적합 모집 0개 또는 독립 표본 ≥10건에서 사전 보유율 <30%이면 주력 채택 중단. 한도/약관 미확인으로 완주할 수 없으면 무인 실행 구현을 보류한다. 표본 부족·30~50% 보유율은 성공으로 올리지 않는다.

## 7. 사용자가 결정해야 할 질문 (최대 5개)

1. **지원 범위:** 민간 SE·인프라에 집중할 것인가, 공공기관·지방공기업도 실제 지원할 것인가? 공무원 시험 경로도 포함하는가?
2. **우선순위 집합:** 지역·고용형태·신입 인정 범위와 관심 기업 5~10곳은 무엇인가? 이 목록을 정해야 관련성 실험의 분모를 고정할 수 있다.
3. **제품의 약속:** ‘승인한 경로의 도착분 처리+독립 표본 누락 공개’를 받아들일 것인가? 매일 수동 보완에 허용할 시간은 10분인가, 그보다 적거나 많은가?
4. **개인 입력·보관:** 이미 받는 공고 메일이 있는가? 있다면 본인 기기에서 20통 감사를 할 수 있는가? 이후 OAuth 접근·개인 메일 원본의 보관 위치/기간을 어디까지 허용할 것인가?
5. **다음 검증 선택:** 세 실험 중 하나를 선택하고 필요한 신청·제한된 실제 호출을 진행할 것인가? 기업/사람인 문의 발송이 필요해지면 별도로 명시 지시할 것인가?

이 질문들은 결정을 미리 채운 것이 아니다. 메일 접근·키 신청·외부 문의·실호출은 이번 문서 검토 범위 밖이며 실행하지 않았다. A~F와 C6의 금지 경계, 제품 약속 변경, 새 입력 구조는 이 보고서만으로 승인되지 않는다.

## 8. 검증·남은 문제·다음 행동

- 변경 파일은 이 문서 하나다. 발산 문서·기능 코드·의존성·게이트는 수정하지 않았고 commit·push하지 않았다. 문서 작업이므로 TDD 실패→구현→통과는 대상이 아니다.
- 외부 검증: 공식 URL 2개 시도 중 P1 재확인 성공, 사람인 도움말 도구 오류 1건. 발산 문서의 실험·실제 메일 품질·실제 키·시장 포함률은 확인되지 않았다.
- 정적 검사: 25개 아이디어의 7축 수정 점수, 후보 3개, 질문 5개, Markdown 표 열수 일치를 Python으로 확인했으며 종료 코드 0이었다. `git diff --check`도 종료 코드 0이었다.
- `make check`: 종료 코드 0. Docker DB healthy, ruff lint·53파일 포맷 검사·mypy 24파일 통과, 백엔드 `189 passed`, 웹 ESLint·TypeScript·Vitest `1 passed`를 확인했다. 검사 실패는 없었다. 이 결과는 기존 코드 회귀 검사이며 제안한 실험의 성공 증거는 아니다.
- 다음 행동: 코디네이터가 사용자 질문을 수렴하고 후보 1의 메일 표본 감사부터 제안한다. 기존 메일이 없거나 민간보다 공공기관이 우선이면 조건에 맞는 후보 2·3의 검증 순위를 다시 정한다.
