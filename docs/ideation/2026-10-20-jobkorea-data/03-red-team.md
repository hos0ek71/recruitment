1. **"비상업이면 괜찮다"는 성립하지 않는다.** 영리성이 요건인 조항은 부정경쟁방지법 성과 무단사용 목(자신의 영업을 위하여)과 저작권법 사적이용 예외뿐이다. 정보통신망법과 사이트 약관은 영리 여부를 묻지 않는다. 확인한 분쟁은 모두 경쟁사·상업 사례이고, 개인 구직자가 상대인 사례는 확인 못 함이다.
2. **형사 위험은 낮고 민사·약관·차단 위험이 남는다(추정).** 대법원 2021도1533은 로그인 없는 공개 정보 수집을 정보통신망 침입으로 보지 않았다. 반대로 사람인 사건은 정체 은폐·IP 우회·공개 재게시가 겹친 사례다. 하루 3~4요청은 여기어때 사건(1,594만 회)의 약 2.6만~3.5만분의 1이지만, 건수는 안전의 증거가 아니다.
3. **가장 큰 가중 요소는 차단 우회와 신원 은폐다.** 그래서 "차단 시 중단"은 위험을 가장 크게 줄이는 조건이다. 여기에 정직한 사용자 에이전트, 비로그인, 비공개 보관, 공개 재게시 금지를 더해야 한다.
4. **robots.txt(2026-08-21판)는 허락이 아니다.** Scrapy를 포함한 스크레이퍼 8종과 AI 학습 봇 22종은 전면 차단이고, Claude-User 등 AI 검색·인용 봇 10종은 일반 규칙(`*`)과 같다(비공개 경로만 차단). 목록·검색 경로는 막혀 있지 않지만, 허용으로 읽으면 안 된다.

### 4.2 해석

1. **Scrapy 전면 차단:** 기본 해석은 요청의 사용자 에이전트가 `Scrapy`로 식별되면 모든 경로가 막힌다는 뜻이다. 범용 스크레이핑 프레임워크와 상업 데이터 수집기(CCBot, Diffbot, DataForSeoBot)를 한 범주로 묶은 것으로 보아, **상업적·범용 데이터 수집기는 환영하지 않는다**는 정책 신호로 읽힌다(추정). 일반 지식으로 Scrapy 프로젝트 템플릿은 robots 준수가 기본 켜짐이다(이번에 재확인 안 함).
2. **차단을 이름만 바꿔 피하면 위험하다.** Scrapy 토큰을 안 쓰는 다른 클라이언트는 문자 그대로는 이 그룹에 걸리지 않고 `*`로 간다. 그러나 사람인 1심이 문제 삼은 사실관계(정체 미표시·우회)와 같은 모양이 된다. 법원이 robots.txt 자체를 구속력 있는 기준으로 판단한 것은 확인 못 함이고, 사실관계 중 하나로 인용됐을 뿐이다.
3. **"AI 사용자 에이전트 허용"의 정확한 의미:** 해당 10종은 특별 허가를 받은 것이 아니라 **일반 규칙(`*`)과 같은 대우**를 받는다. 비공개 경로만 막혀 있다는 뜻이다. 반면 학습용 22종은 전면 차단이다. 따라서 "AI 에이전트가 환영받는다"가 아니라 "AI 학습 목적 수집은 거부하고, 사용자 요청에 따른 열람·인용은 공개 경로에 한해 막지 않는다"에 가깝다(추정). 이를 근거로 Claude-User나 ChatGPT-User 이름을 **사칭하면 안 된다**(정체 은폐에 해당).
4. **목록·검색 경로가 robots로 막혀 있지 않은 이유(추정):** 머리 주석대로 검색 결과 색인을 SEO 목적으로 열어 둔 것이다. 소셜 미리보기 봇만 `/Search/`를 막았다. 검색엔진의 색인과 제3자의 반복 자동 수집은 다른 일이고, 이 파일은 후자를 승인하지 않는다.
5. **robots.txt는 접근 허락이 아니다.** 이미 06 문서가 RFC 9309 §1을 인용해 같은 결론을 냈고, 이번에 RFC를 다시 열람하지는 않았다. 반대로 robots가 막지 않은 경로라도 약관(§2.1)과 판례(§2.2)의 위험은 그대로다.
6. **이 프로젝트에 주는 의미:** robots.txt가 Claude-User를 막지 않으므로 "에이전트 브라우징은 robots상 문제없다"는 주장이 나올 수 있다. 그러나 AGENTS.md 불변식(스크래핑·브라우저 자동화 금지)은 그대로 유효하고, 위 3·5가 이 주장을 약하게 만든다. 이 파일은 8월 개정판이라 이후 바뀔 수 있으므로 어떤 결정이든 실행 직전에 다시 읽어야 한다.

| "공고를 내 DB에 두고 AI로 평가해도 개인용이니 괜찮다" | 약관 ④의 "타인에게 제공"과 LLM 사업자 전송이 겹친다. 원본(`raw_posting`) 영구 보관도 합의 조건(폐기)에 비춰 위험 요소다(§3). | 보관 기간·LLM 전송 범위를 결정(§8-4) |
| "빠짐없음을 숫자로 확인한다" | 08 스파이크의 총건수 대조는 사용자가 복사한 텍스트 기준이다. 자동 수집으로 바꿔도 추천순 정렬의 페이지 간 변동, 화면 개편, 광고·파견 영역 경계는 그대로이고, 차단으로 중단되면 일부만 받은 채 끝난다. 불변식대로 완료가 아닌 실패·partial로 남겨야 한다. | 실행하지 않음. 설계 시 partial 처리 명세 |
| "수집량이 작으니 눈에 안 띈다" | 소송 의지가 있는 회사를 상대로 한 가정이다. 개인 상대 소송 사례가 없다는 것은 위험이 낮다는 근거이지, 0이라는 근거가 아니다. | 사례 부재는 확인 못 함임을 유지 |

## 7. 확인 못 한 것

- 잡코리아의 약관 중 크롤링·자동 수집을 명시 금지한 조항(개인회원 약관에는 단어 없음). 푸터 고지, 서비스 이용 안내 등은 열람하지 않았다.
- 비로그인 방문자에 대한 약관 구속력, browse-wrap 판례.
- 사람인 사건의 정확한 선고일·적용 조문(보도마다 "차목", 2심 일자 2017-02/04 불일치). 대법원 확정일도 보도마다 다르다(2017-08-24 확정 보도, ZDNet 2017-09-27 기사).
- 야놀자 민사 2심의 근거 조항과 상고심 결과.
- 제94조 ①의 제30조 준용이 자동 수집 복제에 적용되는지에 대한 판례. 대법원 2011도5835 원문.
- 대법원 2021도1533 판결문 원문(PDF 열람 실패). 평석·보도로 갈음했다.
- 개인 구직자를 상대로 한 크롤링 소송·형사 사례의 유무(검색 범위 한정, 부재 단정 아님).
- 잡코리아 전체 공고 수(DB 상당 부분 비율 산정 불가).
- 잡코리아가 현재 쓰는 기술적 차단(Cloudflare 등)의 종류와 임계값.

## 8. 사용자가 결정할 것

1. **불변식 유지 여부.** "스크래핑·브라우저 자동화로 채용 사이트를 수집하지 않는다"를 그대로 둘지, 잡코리아에 한해 예외를 둘지. 이 문서는 형사 위험이 낮다는 판단(추정)을 주지만 민사·약관·차단 위험을 없애지 못한다. 예외를 둔다면 설계 문서와 다른 결정이므로 사용자 승인이 필요하다.
2. **수용할 위험의 종류.** (a) 약관 위반 가능성, (b) IP·세션 차단, (c) 민사 청구 가능성 중 무엇을 받아들일 수 있는가. 현실적으로 가장 가능성이 높은 결과는 차단이다(추정).
3. **허락을 구할 것인가.** 가장 확실한 위험 제거는 잡코리아의 서면 허락이다. 이번 회의에서는 문의 발송이 금지였고 Open API는 개인에게 거절될 수 있다고 안내돼 있다. 문의 자체를 사용자가 직접 할지(문의 문구 작성은 가능), 하지 않을지.
4. **저장·AI 사용 범위.** `raw_posting`을 영구 보관할지 기간을 둘지, 공고 원문을 외부 LLM에 보내도 되는지, 담당자 연락처 같은 개인정보 필드를 저장하지 않을지.
5. **정지 조건.** 차단 신호의 정의(403, 429, CAPTCHA, 빈 결과, 구조 변경)와 정지 후 재개 규칙(자동 재개 금지, 사용자 확인 후 재개 등), 사용자 에이전트에 정직한 식별자를 쓸지(사칭 금지).
6. **변호사 상담 여부.** 저작권·IT 전문 변호사 1회 확인이 필요한지. 확인하려면 §7의 목록이 질문 목록이 된다.
7. **서비스 범위 고정.** 1명 전용이 깨지는 순간(다른 사람 공유, 공개 배포, 유료화)에는 §3의 위험 평가가 무효가 되므로 재심사한다는 규칙을 둘지.
8. **robots.txt 해석 기준.** Claude-User 허용을 근거로 에이전트 브라우징을 정당화하는 해석을 쓰지 않는다는 원칙을 확정할지(권고: 쓰지 않음).

## 10. 작업 기록

- 변경한 파일은 이 문서 하나다. git commit·push, 계정 생성, 문의 발송, API 신청은 하지 않았다. 잡코리아 공고 목록·상세·검색 결과는 요청하지 않았고, robots.txt는 조회 도구로 1회, 명령줄로 1회(같은 내용 재확인) 읽었다.
- 법령 조문은 법제처 공개 API로 조회한 현행 원문이다. 판결은 평석·보도 기반이라 원문과 다를 수 있다.
- 코드 변경이 없어 `make check`는 실행하지 않았다.
