# MVP 설계 문서 검토

대상: `공채 모아보기 MVP 설계 문서.md` (2026-10-17 판) · 검토: 2026-10-17

## 결론

방향은 좋다. 결정적 파이프라인을 코드로 돌리고, AI 범위를 세 곳으로 묶고, 탈락 사유 코드와 쿼리별 완전성 검증을 둔 것이 MVP 목표("빠짐없이, 근거와 함께")와 맞는다.
외부 API 주장 47개를 공식 문서와 대조했다. 틀린 것은 없지만 9개는 조건이 빠져 있거나 과장되어 있다.

가장 큰 위험은 **데이터 소스 확보**다. 고용24 Open API는 기업회원 전용이고 담당자 심사를 거친다. 사람인 신청서는 회사명이나 학교명을 요구하고, 개인 허용 여부가 문서에 없다. 그래서 리스크 표의 "사람인이 늦어지면 고용24로 먼저 개발"이라는 대응이 성립하지 않을 수 있다. 키 확보를 구현 전 첫 과제(P-0)로 둔다.
그 밖에 구현 전에 정해야 할 결함이 7개 있다. 대부분 데이터 모델과 수집 기준점 문제다. 지금 정하지 않으면 1단계(수집) 스키마를 다시 만들어야 한다.

**잘된 점:** 원본과 정규화 분리, 조건 버전별 필터 결과, '정보 없으면 통과 + 확인 필요' 원칙, 실패 쿼리를 숨기지 않기, AI 출력 JSON 스키마 검증, 실제 응답 픽스처 테스트, 키를 환경변수로만 다루기.

## 1. 구현 전에 결정해야 할 것

> **확정 (2026-10-17, 사용자):** D1~D7은 아래 "제안" 열의 기본값으로 진행한다. 추천 임계값 60점, 일일 예산 400회(추가 탐색 예약 100회), 활성 공고는 재수집에서 다시 보이지 않으면 `last_seen_at` 기준으로 만료, 마감 처리는 정규화 직후로 옮긴다. S1~S14의 스키마 보완 필드도 C-1에 넣는다. 값은 나중에 마이그레이션으로 바꿀 수 있다. D0(API 키)과 D6(접근 제한 방식)은 아직 미정이다.

| D3 | AI 사용 범위, 결과 API | "추천"의 기준이 없다. 점수 몇 점부터 recommended인지, 평가 대기·실패 공고는 어느 그룹인지 정해져 있지 않다. | 추천 임계값(예: 60점)을 조건 버전에 저장한다. `pending_evaluation`, `evaluation_failed` 상태를 정의한다. |

| D5 | 제약(64행), 파이프라인 1단계(94행), 실패 처리(106행) | 호출 한도 정책이 세 곳에서 서로 다르다. 400회를 넘으면 멈춤, 예상 호출 수가 한도를 넘으면 실행 안 함, 한도 오류가 나면 미루고 partial. 게다가 첫 페이지를 받기 전에는 총건수를 몰라서 예상 호출 수를 정확히 계산할 수 없다. | 하나로 통일한다. 일일 예산 400회(추가 탐색용 100회 예약), 쿼리 우선순위대로 예산 안에서 실행, 남은 쿼리는 deferred로 기록하고 partial. 예상 호출 수는 직전 `total_reported`로 추정한다. KST 일자별 호출 원장(`api_usage`)을 둔다. |

| D7 | 수집 파이프라인 6~8단계 | 마감 처리(8단계)가 필터(6)와 AI 평가(7) 뒤에 있다. 이미 마감된 공고를 평가해서 비용을 쓰고, EXPIRED 판단이 늦어진다. | 마감 처리를 정규화 직후(5단계 뒤)로 옮긴다. |

## 2. 구현하면서 반영할 명세 보완

| # | 위치 | 문제 | 제안 |
| --- | --- | --- | --- |
| S1 | MVP 목표 4 | "매일 새로 올라온 공고만"을 보여주는 API 파라미터와 화면이 없다. | `/results`에 `since`(또는 `new=today`)를 추가하고 `first_seen_at` 기준으로 거른다. 결과 화면에 "오늘 새 공고" 필터를 둔다. |
| S2 | 사용자 흐름 7, 확정 필터 | 제외 회사·사용자 표시가 바뀌어도 조건 버전별로 계산한 `filter_result`는 그대로라 결과가 낡는다. 지원함으로 표시한 회사가 결과에서 빠지면 지원한 공고 자체를 추적할 수 없다. | EXCLUDED_COMPANY는 조회 시점에 적용하거나, 변경 시 해당 회사 공고만 다시 거른다. "지원함" 목록 화면을 따로 둔다. 표시 → 제외 회사 자동 등록 규칙을 적는다. |
| S3 | 데이터 모델 | 빠진 필드와 테이블이 있다. AI 평가 입력에 직무 코드가 있지만 `posting`에 없다. 중복 판단에 쓴다는 고용24 정보제공처 필드도 없다. 추가 탐색 키워드와 도구 호출 기록을 저장할 테이블이 없는데 실행 기록 화면에는 보여준다고 되어 있다. 평가 프롬프트 버전과 평가 상태도 없다. | `posting.job_codes[]`, `posting.provider`(정보제공처), `explore_keyword(keyword, status, criteria_id)`, `tool_call_log(run_id, tool, input, output)`, `evaluation.prompt_version`, `evaluation.status`를 추가한다. |
| S4 | 중복 병합 | "마감일이 같으면"의 빈 값 처리가 없다. 상시채용끼리, 한쪽만 마감일이 없는 경우가 정해지지 않았다. 병합 시 어느 소스의 필드를 쓸지도 없다. 사람인에는 사업자번호가 없어서 교차 소스 병합은 회사명에만 의존한다. | 빈 마감일 규칙과 필드 우선순위(예: 사원수·사업자번호는 고용24, 경력 범위는 값이 있는 쪽)를 정한다. 병합 내역을 상세 화면에 보여준다(리스크 표의 대응과 같음). |
| S5 | 조건 승인, API | 승인된 조건을 PATCH하면 어떻게 되는지 없다. 새 버전을 만들면 통과 공고 전체를 다시 평가하게 되어 "비용은 새 공고 수에만 비례"와 충돌한다. | 승인된 조건은 수정 불가, 수정하면 새 draft 버전을 만든다. 재평가 범위를 정한다(예: 평가 입력이 바뀐 경우만, 또는 키워드 변경은 재평가 안 함). |
| S6 | 스케줄러 | APScheduler를 앱 프로세스 안에서 돌리면 uvicorn 워커 수만큼 작업이 중복된다. 수동 실행이나 추가 탐색과 겹치면 한도를 두고 경합한다. | API는 워커 1개로 띄우거나 스케줄러를 별도 프로세스로 둔다. 실행은 PostgreSQL advisory lock으로 한 번에 하나만 돌린다. |
| S7 | API | `POST /criteria/{id}/approve`가 즉시 수집을 돌리면 요청이 길어진다. | 백그라운드로 실행하고 `run_id`를 바로 돌려준다. |
| S8 | 수집 파이프라인 2단계 | 페이지를 넘기는 동안 새 공고가 들어오면 페이지가 밀려 중복이나 누락이 생긴다. | `items_received`는 고유 ID 기준으로 센다. 가능하면 등록일 오름차순처럼 안정적인 정렬을 쓴다. |
| S9 | 기술 스택 (pg_trgm) | pg_trgm은 로캘이 문자로 인식하지 않는 글자를 버린다. DB 로캘에 따라 한글 제목의 유사도가 계산되지 않을 수 있다(확인 필요). | C-1에서 한글 제목 유사도 테스트로 확인한다. 안 되면 로캘을 바꾸거나 정규화 문자열 비교로 대체한다. |
| S10 | 확정 필터 HEADHUNTING | 수집 단계에서 빠지므로 탈락 건수에 잡히지 않는다. 사람인이 미리 뺀 공고는 응답에 없어서 개별 사유를 남길 수 없다. 고용24에는 같은 옵션이 없다. | 파라미터 `sr=directhire`를 명시한다. funnel에 "수집 단계 제외(건수 모름)"로 따로 표시하고, 받지 않은 공고로 탈락 기록을 만들지 않는다. 고용24 파견은 EMPLOYMENT_TYPE으로 거른다. |
| S11 | 데이터 소스, 데이터 모델 | 고용24 사원수는 목록 응답에 없다. 상세 API의 `corpInfo.totPsncnt`에 있다. 목록의 `workerCnt`는 검색 조건이다. 반대로 상세 API에는 담당업무(`wantedInfo.jobCont`)가 있어서 리스크 표의 "보완 가능 여부"가 해결된다. | 필터를 통과한 고용24 공고만 상세를 호출해 `employee_count`와 담당업무를 채운다. 상세 호출도 일일 예산에 넣는다. |
| S12 | 수집 파이프라인, 기술 스택 | 고용24는 목록과 상세 모두 `returnType=XML`이 필수이고 JSON 지원은 명시되어 있지 않다. 페이지 상한도 있다. 고용24는 `startPage` 1~1000, `display` 최대 100이고, 사람인은 `start`가 0부터 시작하는 페이지 번호, `count` 최대 110이다. | 고용24 어댑터에 XML 파서를 두고, 원본은 XML 텍스트로 보존하거나 변환한 JSON과 함께 저장한다. 페이지 상한에 닿으면 완료가 아니라 partial로 남기고 쿼리를 나눈다. |
| S13 | 실패 처리 | 사람인의 일일 한도 초과는 응답 `code=4`다. 400회 중단은 공식 한도가 아니라 자체 예산이다. 고용24 일일 한도는 공개 문서에서 확인하지 못했다. | 오류 매핑에 `code=4`를 적는다. 고용24 한도는 키를 받은 뒤 확인하고, 그전에는 설정값으로 둔다. |
| S14 | 출처, 이용 조건 | 참고 설계 `job-platform-mcp`는 현재 Playwright로 공개 검색 화면을 읽는 브라우저 기반 구현이다. 고용24 상세 문서는 제공사이트 이동 버튼과 출처 표시를 요구한다. | 참고 저장소를 공식 API 근거에서 뺀다. 결과·상세 화면에 출처 표시를 넣는다. |

## 3. 문서 자체의 문제

- 임베드 3개(시스템 구성도, 결과 화면 와이어프레임, MVP 로드맵·게이트)의 내용이 md에 없다. 특히 **게이트 기준이 문서에 없다.** `docs/harness/features.json`의 단계·게이트는 본문에서 추정한 것이므로 원본 그림과 대조해서 확정해야 한다.
- 4단계(선택)에 무엇이 들어가는지 본문에 없다. features.json에서는 추가 탐색(X-1)을 4단계로 두었다.
